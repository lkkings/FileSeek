## Context

Current list rows and grid cards use simulated backgrounds or generic category icons. The detail drawer shows a simulated scene, and opening a file delegates to the operating system. The backend already streams original file bytes with MIME detection and HTTP range support, while the frontend already depends on `pdfjs-dist`, `xlsx`, and `video.js`. No reusable preview feature, thumbnail API, or binary transport for packaged Tauri builds exists.

## Goals / Non-Goals

**Goals:**

- Provide consistent previews for file lists, grids, the detail drawer, and in-app full-screen viewing.
- Keep preview logic in a dedicated frontend feature instead of duplicating it across search, recent, and library components.
- Generate cached image and video thumbnails without loading original media into every visible list row.
- Keep backend authentication credentials outside the WebView in packaged builds.

**Non-Goals:**

- Server-side conversion of legacy Office or ODF documents.
- Editing, annotating, or persisting document changes.
- Replacing the existing original-file streaming endpoint.
- Generating thumbnails for documents; document list cells use format icons.

## Decisions

### Frontend feature boundary

Create `desktop/src/features/file-preview` with preview classification, URL construction, format-specific icons, document/image/video preview components, and the in-app viewer surface. `FileListRow`, `FileGridItem`, and `FileDetailDrawer` consume its public exports. Pages and feature components must not each implement their own preview branching.

Alternative considered: extending each list component with preview logic. That would duplicate format decisions and make search, recent, and library behavior drift.

### Document rendering with AnyView

Add `anyview` and the optional peer dependencies needed for the formats the product accepts: PDF, DOCX, XLSX, PPTX, CSV, Markdown, HTML, text, and code-like documents. Use `DocViewer` with a URL source:

- Detail drawer: controlled first page, no toolbar/sidebar.
- Full-screen viewer: toolbar, sidebar, search, zoom, and navigation enabled.

Formats outside the preview support list, including `.doc`, `.xls`, `.ppt`, `.xml`, `.odp`, `.ods`, and `.rtf`, use a format-specific fallback and explanatory state. Existing `pdfjs-dist` and `xlsx` versions should satisfy AnyView's peer ranges after dependency installation.

Alternative considered: separate `pdfjs-dist`, `docx-preview`, and `xlsx` renderers. AnyView provides one source API and a unified viewer, reducing per-format integration code.

### Image and video rendering

Use thumbnail resources for list and drawer previews of JPG, PNG, GIF, BMP, WebP, TIFF, and ICO images. HEIF, HEIC, and SVG show an unsupported-preview state. Use `video.js` for inline detail playback and the full-screen player, with the original-file preview endpoint as the source. The drawer initially renders the video thumbnail; activating playback swaps the thumbnail for the player and preserves the file context.

Alternative considered: using the original image directly in lists. This risks large network and memory usage for high-resolution files and NAS-backed sources.

### Backend thumbnail API

Add a library route such as `GET /library/files/{file_id}/thumbnail?size=list|detail`. A use case resolves the file, validates its category, and delegates generation to an infrastructure thumbnail service:

- Images: decode with Pillow, preserve orientation, resize, and encode WebP.
- Videos: decode a representative early frame with PyAV, resize, and encode WebP.

Cache generated bytes in an application cache directory keyed by file id, source size, modified time, and requested size. Return cache-friendly response headers. Do not store thumbnail bytes in the database; this avoids a migration and keeps generated assets disposable.

Alternative considered: persisting extracted keyframes from the indexing pipeline. The current pipeline discards frame bytes and only stores timing metadata, so retrofitting storage would require a larger data-model change.

### Binary transport for Tauri

Keep the Vite proxy for browser development. For packaged Tauri builds, register a WebView-accessible preview URI scheme/protocol in Rust that:

1. Accepts only preview paths supported by the app.
2. Reads the backend port and token from the trusted connection state.
3. Forwards requests, including `Range`, to the backend.
4. Returns binary bytes, content type, content length, range, and cache headers to the WebView.

The preview feature resolves a URL appropriate to the current runtime. The token remains in the Rust process and is never exposed to page scripts.

Alternative considered: returning preview bytes through the existing JSON `api_request` command. That command is designed for JSON responses and would force whole-file buffering, break video range seeking, and increase memory use.

## Risks / Trade-offs

- [AnyView maturity and optional peers] → Pin a known compatible version, install only required parsers, and isolate it behind the file-preview feature so it can be replaced without changing list contracts.
- [Unsupported legacy documents] → Show explicit unsupported states; do not silently invoke the operating system because the required behavior is in-app opening.
- [Thumbnail generation cost] → Generate asynchronously outside request hot paths where possible, cache by file metadata, and return fallback states while generation is unavailable.
- [Video codec and remote filesystem failures] → Bound decode time, validate output dimensions, and return category fallbacks on failure.
- [Custom preview protocol complexity] → Keep the protocol narrowly scoped to preview resources, preserve range headers, and test both development and packaged transports.
- [Large inline players in the drawer] → Mount the player only after activation and dispose it when the selected file changes or the drawer closes.

## Migration Plan

1. Install and verify AnyView and required peer dependencies.
2. Add backend thumbnail generation and tests.
3. Add the preview URL abstraction and Tauri binary transport.
4. Build the file-preview feature and integrate list/grid/drawer surfaces.
5. Add the full-screen in-app viewer and wire open actions.
6. Run focused frontend, backend, type, and lint checks.

Rollback is limited to preview integration and generated cache files; no database migration is required. Removing the feature exports and preview route disables the new behavior without changing core file indexing or search data.
